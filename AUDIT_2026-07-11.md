# Technical audit of the FPL pipeline — 2026-07-11

Full repository review commissioned by the PO: methodological weaknesses, architecture,
statistical errors, hidden leakage, maintainability, simplification opportunities, and
opportunities for higher predictive/optimization quality. Everything below was verified against
actual code lines and data (not assumed from the documentation). The actionable follow-up lives
as a dependency-ordered todo in `TODO.md` ("Audit follow-ups 2026-07-11"); this report is the
rationale behind each item.

**Scope:** all of `fpl/` (data, features, models, MILP, run_week), all 11 test files,
`RESEARCH_LOG.md`, `HANDOFF.md`, `TODO.md`, `CLAUDE.md`/`AGENTS.md`, `experiments/results.csv`,
the CI setup, git state, and `master_dataset.csv` (162,981 rows, GW_global 1–228,
2020-21 through 2025-26).

---

## 1. Mental model of the system

**Data flow:** `fpl/data/fetch.py` (vaastav data, dynamic season/GW discovery, name/team
corrections, FDR merge, `GW_global` as a season-ordinal counter) →
`Datasett/master_dataset.csv` → `fpl/features.py` (~115 columns: shifted rolling windows, two
expanding-mean horizons, EWMA, per-90 rates, nailedness, opponent form, shifted xP, unshifted
fixture features) → per-position model registry (`fpl/model/models.py`, 12 types; production =
Optuna-tuned CatBoost alone, chosen empirically by the bake-off in `train.py`) → walk-forward
predictions CSV (`predict.py`) → Kristiansen MILP (`fpl/milp/optimize.py`, PuLP+CBC, rolling
horizon) → realized points. In parallel: the quantile module (`probabilistic.py`) and the
bucket module (`probabilistic_buckets.py`), both forecasting-only. `run_week.py` is the live
path (official FPL API for fixtures/squad/bank).

**Evaluation discipline:** MASE + decision-aligned diagnostics (RMSE, bias,
total_calibration, Spearman per position-GW, top1_capture); gold standard = realized MILP
points on GW153-183 (2024-25 GW1-31), standing baseline **2107** (tuned CatBoost). Combination
weights/calibration are always fit strictly before the prediction window
(`fit_holdout_weights`). Experiments are logged to `experiments/results.csv` +
`RESEARCH_LOG.md`, negative results included.

## 2. Strengths (the context the critique stands in)

- The leakage discipline is well thought out and **tested** (`test_features_advanced.py` is a
  real leakage guard that tampers with outcomes and asserts unchanged features).
- The mean-vs-median trap is identified, explained, and demonstrated empirically three times —
  and it changed the decision rule (realized points > MASE).
- Negative results are reported consistently (Croston, Theta, ARIMA, EB shrinkage, level
  calibration, all the bucket ensembles) — unusually good research hygiene.
- `RESEARCH_LOG.md` makes results traceable to hypothesis, code, and numbers without digging
  through git history.

The critique below does not weaken the *relative* research results (CatBoost > blend, buckets
lose in the MILP, etc.) — the protocols were identical on both sides of every comparison. It
concerns the absolute level, the live path, and the measurement system itself.

---

## 3. Findings A — Bugs and correctness

### A1. The live path does not run the validated production configuration ("training-serving skew")

- **What:** `run_week.py:223` fits members with `fit_model(name, X, y)` **without**
  `position=pos` → the Optuna-tuned parameters (the entire +251-point gain) are never loaded in
  live mode. `run_week.py:217` uses the default strategy `"nnls"` (the 12-member blend that
  lost to CatBoost at every position), not the bake-off winner. On top of that,
  `train.train_final_ensembles` saves production ensembles to `fpl/models/<POS>.*` that
  **nothing ever loads** — `PositionEnsemble.load` has zero call sites. There are three
  different definitions of "the production model"; only the backtest path is the one that
  scored 2107.
- **Why it matters:** live 2026-27 would run a ~1856-level configuration while all the
  documentation says 2107.
- **Impact:** large. **Complexity:** hours. **Trade-off:** none.
- **Basis:** classic MLOps failure category (training-serving skew); readable straight off the
  code.

### A2. The tuning CLI cannot reproduce its documented result — a re-run would leak

- **What:** `RESEARCH_LOG.md` (2026-07-06) says CatBoost was "tuned on GW<153 only", but
  `fpl/model/tuning.py` has **no** GW cap: `tune_position` folds over all gameweeks, so a
  re-run today would validate hyperparameters on GW153-228 — including the backtest window.
  (The bucket tuner has an explicit `train_max_gw=152`; the regression tuner lacks it.)
- **Impact:** medium-large — 2107 rests on these parameters; the reproducibility of the
  project's most important result is a matter of trust. **Complexity:** hours.
- **Open question for the PO:** was the July run done against a temporarily truncated dataset?
  The answer decides whether this is a documentation gap or the result needs re-verification.

### A3. Double-gameweek leakage in all shifted player features

- **What:** `shift(1)` in `features.py` is per *row*, not per *gameweek*. In a DGW a player has
  two rows with the same `GW_global`; row two's "form" includes fixture one **from the same
  round** — information that does not exist when the squad locks before the round. Measured in
  the dataset: 6,950 player-GWs with >1 row; **8.6% of all rows sit in DGWs**. `sort_values` is
  also not stable, so which fixture counts as "first" is arbitrary.
- **Why it matters:** DGW players are exactly the ones the MILP hunts (double points
  potential), so the backtest optimism concentrates where the decisions are made.
- **Impact:** small but systematic upside in the backtest; a genuine violation of the
  project's own leakage rule. **Complexity:** ~1 day + a re-baseline of 2107.

### A4. Live mode: stale prices, no injury data, DGWs counted as one fixture

- **(a) Prices:** the snapshot's `value` is the price from the last *played* round in
  vaastav's dump, not `now_cost` from the bootstrap API — deadline budget math can be wrong.
- **(b) Availability:** the API's `status`/`chance_of_playing_next_round` are unused — an
  injured player with good rolling form gets bought happily. This is the cheapest free win in
  the repo for live play.
- **(c) DGW:** `build_team_fixture_map` keeps only the first fixture of a double gameweek
  (the backtest sums per fixture) — live systematically undervalues DGW players.
- **Impact:** medium-large for live 2026-27; zero for backtests. **Complexity:** 1-2 days
  total.
- **Basis:** every serious community FPL model treats availability as a first-class signal.

## 4. Findings B — Evaluation methodology and statistics

### B1. One decision window reused for every choice — winner's curse on GW153-183

- **What:** every choice since June (model type, combination strategy, features, bucket
  scheme, tuning verification) has been judged on the same 31-GW window, dozens of times. Even
  with honest training discipline per run, the *selection across runs* overfits the window;
  2107 is likely optimistic as an estimate of true skill.
- **The solution is already sitting in the data:** 2025-26 (GW191-228) is complete and nearly
  untouched (used once in a catboost-vs-blend comparison at the MASE level, never at the MILP
  level). Freeze GW191-221 as a **one-shot confirmation window**: run the frozen production
  config there once, report the number whatever it is, never use the window for selection
  afterwards.
- **Impact:** large for credibility. **Complexity:** pure compute.
- **Basis:** standard holdout discipline; "garden of forking paths" (Gelman & Loken).

### B2. The backtest has lookahead optimism live mode cannot match

- **What:** in the backtest, GW t+1/t+2 are predicted with features that include the outcomes
  of GW t and t+1. The MILP at t uses these in its lookahead terms, and they influence the
  transfer that gets locked in — the decision at t is informed by data realized *after* t.
  Live mode freezes form at "now" for the whole horizon. The backtest protocol therefore
  measures a system with better lookahead than anything deployable.
- **Impact:** unknown size, certain direction (2107 is too high as a live expectation).
  Old-vs-new comparisons remain fair (same protocol on both sides).
- **Fix:** origin-based multi-step forecasts (for each origin GW t: predict t..t+h with
  features frozen at t). **Complexity:** 1-2 days.

### B3. 48-point verdicts without an uncertainty measure

- **What:** the bucket model was parked on −48 (2059 vs 2107) on one window; no comparison has
  ever carried an uncertainty interval. With per-GW realized points for both configurations, a
  paired block bootstrap over gameweeks (or a sign test) is nearly free.
- **Impact:** medium — calibrates every future ±50 verdict. **Complexity:** hours.
- **Basis:** the Diebold-Mariano tradition; paired bootstrap is production standard.

### B4. The MASE scale is inconsistent across modules

- **What:** `train.py` uses one *global* naive scale (pooled across positions) for
  per-position MASE; `tuning.py` uses *per-position* scales. The "FWD is hardest
  (MASE 1.07 > 1)" finding really just says FWD has the highest MAE against a shared
  denominator — not that the model loses to FWD's own naive forecast. Numbers across modules
  are not comparable.
- **Impact:** small on decisions (MASE is demoted to a secondary metric), but a real ambiguity
  in a headline number in the report. **Complexity:** hours.

### B5. Realized points ignore auto-subs and vice-captain activation

- **What:** backtest scoring is lineup + captain; real FPL substitutes bench players for
  non-playing starters and activates the VC when the captain doesn't play. All configurations
  are understated equally (fair comparison), but absolute numbers against "real managers"
  percentiles are skewed.
- **Impact:** small; mainly a reporting footnote, possibly a simple auto-sub simulation
  (~1 day).

## 5. Findings C — Opportunities for better prediction (ranked)

### C1. Dedicated minutes model (two-stage: E[minutes] × points per 90)

59% of rows are 0-minute rows, and the loss-probability analysis showed blank prediction is
dominated by the minutes signal. Today's `start_rate_roll5` is a lagged proxy; an explicit
P(start)/E[min] model feeding the points model is the standard architecture in strong FPL
systems. **Impact:** probably the largest single gain. **Complexity:** 3-5 days.
**Basis:** hurdle-model literature + community practice. **Verification:** MILP backtest.

### C2. Use the current GW's `xP` directly

xP is by definition a pre-match quantity; using GW t's xP for GW t is legitimate **if** the
stamping in vaastav's dumps is verified first (check whether raw xP correlates with outcomes
beyond the plausible). FPL's own model as a free feature. **Impact:** small-medium.
**Complexity:** hours + verification. **Trade-off:** post-match stamping in some seasons =
leakage; hence the verification.

### C3. Ranking objective (LambdaRank per GW-position)

Three "better metrics bought fewer points" episodes all point the same way: the MILP
effectively consumes *ranking*. Natural experiment: train directly on ranking (LightGBM
lambdarank grouped per GW-position), map monotonically to the points scale for the MILP's
absolute-scale terms. **Impact:** uncertain, but hypothesis-driven by the project's own
findings. **Complexity:** 1-2 days. **Trade-off:** another negative result is entirely
possible.

### C4. Fair tuning of LightGBM/XGBoost

The registry ranking is currently tuned-vs-defaults; "CatBoost is best" is partly default
luck. Already an open thread in HANDOFF. **Complexity:** mostly compute.

### C5. Bookmaker odds as features

Clean-sheet/anytime-scorer odds are the strongest exogenous signal in the football-prediction
literature; FDR is static and coarse. **Impact:** potentially large. **Complexity:** large
(historical odds archives, acquisition, merge) — low priority despite the high ceiling.

*(Pruning the 115 collinear feature columns is possible, but the gain is mostly training
speed — the trees can keep them for now.)*

## 6. Findings D — Optimizer

MILP work is deliberately parked (the Venter read supports that), so only:

- **D1. Rule currency before live 2026-27:** `Q_bar=2` (now 5 banked FTs), the sell-price
  rule (purchase price + half the profit), and the fact that chips are effectively dead code
  in backtests (all disabled → 2107 is a zero-chips number; real seasons carry ~100+ chip
  points outside the model). The FT rule is one line + a backtest; the rest can be documented
  as a limitation.
- **D2. Duplicated FT/chip accounting:** the solver has FT logic in constraints and the
  Python loop (`optimize.py:373-386`) reimplements it to roll state forward. A divergence
  would be silent and ugly; the test only covers budget/position/club/formation, not transfer
  penalties/chip state. A test running 5-6 GWs and asserting the FT trajectory closes the
  class. **Complexity:** hours.

## 7. Findings E — Architecture, maintainability, reproducibility

- **E1. Three near-identical walk-forward loops** (`predict.py`,
  `probabilistic_buckets.evaluate_walk_forward`, `walk_forward_predictions_csv`) + two
  near-identical member-training loops (`fit_holdout_weights`, `fit_level_calibration`). One
  shared harness removes the most important divergence risk in the repo — A1 is exactly that
  class of divergence. **~1 day.**
- **E2. Reproducibility:** `requirements.txt` is unpinned (`>=`); `experiment.py` logs the
  git hash but not library versions or data state (max GW/row count). A CatBoost version bump
  can silently move 2107. Pin (lockfile) + log `catboost.__version__` and `max_gw` per
  experiment. **Hours.**
- **E3. Git bloat:** `.git` is 159 MB because `master_dataset.csv` (33 MB, regenerable) is
  tracked and re-committed. Gitignore it; keep the thesis-era raw files. History rewriting is
  optional and the PO's call. **Hours.**
- **E4. Packaging hygiene:** the `sys.path.insert` hack in every module → `pyproject.toml` +
  `pip install -e .`. Portfolio signal > functional value. **Hours.**
- **E5. Slow train.py:** the rejected baselines (Theta refits polyfit per row, per-player
  ARIMA) run on every `fpl.model.train` invocation. Gate behind `--with-baselines`.
  **Hours.**
- **E6. Feature cache:** `build_feature_frame` is recomputed from scratch in every
  entrypoint; a parquet cache keyed on (dataset hash, feature version) cuts iteration time.
  **Hours.**
- **E7. Documentation drift:** `CLAUDE.md`/`AGENTS.md` are near-duplicates (AGENTS lacks the
  PO sections); `README.md` still says `legacy/` holds the R code (deleted); the report cites
  stale numbers (known in TODO). One canonical source + pointers. **Hours.**
- **E8. Data-quality guards in fetch.py:** FDR merge coverage and duplicate rows are not
  asserted (violates the repo's own "log shapes after joins" rule);
  `fetch_fixture_difficulty` uses `iterrows` (violates the repo's own vectorization rule,
  harmless at this scale). Name-based player identity is a known weakness — an element-ID
  join is the right long-term answer, especially for live matching where name mismatches
  currently drop players silently.

## 8. Prioritized roadmap (return per engineering hour)

| # | Action | Effort | Expected effect |
|---|--------|--------|-----------------|
| 1 | A1: Fix live parity (position param, strategy, one code path) | hours | Protects the value of everything else in live use |
| 2 | B1: Confirmation backtest on the frozen 2025-26 window + B3: bootstrap uncertainty | compute + hours | Makes the 2107 claim credible; calibrates future ±50 verdicts |
| 3 | A2: `--train-max-gw` in tuning + version logging (E2) | hours | Closes the reproducibility gap in the project's most important result |
| 4 | A3: GW-level shift (DGW leakage) + re-baseline | 1 day | More honest baseline; small but real correction |
| 5 | B2: Origin-based horizon backtest | 1-2 days | The honest deploy number; measures the lookahead gap once |
| 6 | C1: Minutes model | 3-5 days | Largest likely forecast gain |
| 7 | A4: Live price/injury/DGW fixes (before the 2026-27 season) | 1-2 days | Required for trustworthy live recommendations |
| 8 | C2/C4: xP verification; tune LGB/XGB | hours/compute | Cheap, well-scoped experiments |
| 9 | C3: LambdaRank experiment | 1-2 days | Tests the ranking hypothesis the project itself established |
| 10 | E1/E5/E6/E7/E3: consolidation and hygiene | ~2 days | Maintainability + portfolio polish |

The 1-5 ordering is deliberate: **they repair the measurement system before it is used to
judge new models** (items 6+). Building the minutes model first and judging it against a
baseline with known DGW leakage and lookahead optimism would repeat the pattern that produced
the inflated 1966 headline.
